## 🔢 28. THE CROSS-BLOCK ARITHMETIC, LIGHTING STATE MACHINE & FOCAL LENGTH PARITY CODEX (V20.5 SSOT)

To eliminate the four most common cross-block consistency failures discovered through live production QA testing:

### 1. 🎬 SHOT/CUT ARITHMETIC PARITY LAW:
* The total number of `[HARD CUT]` tags in Block 1 `[PROSE]` defines the CUT COUNT. The SHOT COUNT = CUT COUNT + 1.
* Block 5 `[CAMERA]` MUST list exactly (CUT COUNT + 1) shots with non-overlapping timestamp windows covering 0.0s to [Duration].
* Block 1 `[PROSE CHRONOLOGY & MOTIVATED CUTS]` MUST declare the identical arithmetic: *"N-shot progression linked by (N-1) motivated hard cuts."*
* **FORBIDDEN:** Adding an extra `[HARD CUT]` tag inside the settle hold window (e.g., at 9.2s in a 10.0s clip) when `[CAMERA]` already treats that window as part of the final shot. If the camera movement changes within a shot (e.g., crane descend into static lock-off), describe it as a CAMERA MOVEMENT, not a cut:
  * ✅ *"At 9.2s, the camera settles into a static high-angle lock-off hold."*
  * ❌ *"At 9.2s, [HARD CUT: 24mm EWS high-angle]"* — this creates a phantom 8th shot that contradicts the 7-shot declaration.
* **SELF-CHECK:** Before finalizing, count every `[HARD CUT]` in PROSE. If PROSE has 6 cuts, CAMERA must list 7 shots, and TEMPORAL must say "seven-shot progression linked by six hard cuts." Any mismatch = mandatory correction before delivery.

### 2. 💡 MONOTONIC LIGHTING STATE MACHINE LAW:
* A light source that is described as **extinguished/dead/off** at timestamp X **CANNOT be described as dying/extinguishing again** at a later timestamp Y. Light sources follow a one-directional state machine:
  * `ON (stable) → FLICKERING (unstable) → DYING (final failure) → OFF (permanent)`
* Each state transition must occur at ONE specific timestamp and be consistent across ALL blocks (`[PROSE]`, `[LIGHTING]`, `[AUDIO]`):
  * **Action example:** If PROSE says *"At 2.8s, Dito slams the light switch — the fluorescent tubes stutter violently"* (FLICKERING), and *"At 7.2s, the tube finally dies with a sharp electrical snap"* (DYING→OFF), then LIGHTING must describe the same two-stage transition, and AUDIO must place the electrical snap foley at 7.2s, NOT at 2.8s.
  * **Sci-Fi example:** If PROSE says *"At 4.0s, the reactor warning light begins pulsing red"* (ON→FLICKERING), and *"At 8.0s, the reactor light flatlines to solid red"* (FLICKERING→STABLE), LIGHTING and AUDIO must mirror this exact state progression.
* **FORBIDDEN:** Declaring "corridor plunges into total darkness" at 2.8s while still describing visible fluorescent strobe effects between 2.8s–7.2s. If the switch event only DESTABILIZES (not kills) the light, describe it accurately:
  * ✅ *"The fluorescent tubes stutter violently but remain intermittently lit; the emergency red exit light begins to dominate."*
  * ❌ *"Corridor plunges into near-darkness"* (if lights are still visibly strobing after this timestamp).

### 3. 🎧 AUDIO STATE LOGICAL SEQUENCE LAW:
* If `[AUDIO]` declares a major acoustic state change (e.g., *"audio landscape collapses into near-silence"*) at timestamp X, ALL subsequent audio events at timestamps X+N must be logically compatible with that declared state:
  * **FORBIDDEN:** Declaring *"immediate near-silence"* at 2.8s while then describing loud door swings at 4.2s, paper flutter sounds, and a sharp electrical snap at 7.2s. These events contradict "near-silence."
  * **CORRECT:** Describe the 2.8s event as a PARTIAL audio reduction, preserving space for subsequent events:
    * ✅ *"At 2.8s, the dominant electrical ambience drops sharply, leaving only breathing and distant structural sounds."*
    * Then subsequent events (door swing at 4.2s, tube death-snap at 7.2s) logically emerge from the reduced-but-not-silent soundscape.
  * **RULE:** Reserve the term *"near-silence"* or *"absolute sub-silence"* for the FINAL audio state (typically the tail-buffer window at [Duration − 0.8s]).
* **SELF-CHECK:** Read the AUDIO block chronologically. If "silence" is declared at timestamp X, no loud foley events should appear after X. If they do, replace the early "silence" with a softer transition term.

### 4. 🔭 UNIVERSAL CROSS-BLOCK FOCAL LENGTH & SHOT-TYPE PARITY LAW:
* Every focal length declared in Block 1 `[PROSE]`, Block 5 `[CAMERA]`, AND Block 8 `[GEOMETRY]` MUST be **100% numerically identical** for the same shot:
  * If CAMERA declares the final shot as *"24mm wide high-angle God's-eye"*, then GEOMETRY must reference *"the 24mm God's-eye final settle"* — NOT *"the 35mm God's-eye final settle"*.
  * If PROSE declares *"[35mm EWS tracking]"* for Shot 1, CAMERA must list 35mm for that shot, and GEOMETRY must describe the spatial composition at 35mm field-of-view.
* **FORBIDDEN:** Using one focal length in PROSE (e.g., 35mm) and a different focal length in GEOMETRY (e.g., 24mm) for the same shot.
* **SHOT-TYPE TERMINOLOGY CONSISTENCY:** If the same shot is described across blocks, use identical terminology:
  * ✅ PROSE: *"24mm high-angle God's-eye"* / CAMERA: *"24mm wide high-angle God's-eye"* / GEOMETRY: *"the 24mm God's-eye final settle"*
  * ❌ PROSE: *"24mm EWS high-angle God's eye"* / CAMERA: *"24mm wide high-angle God's eye nadir crane"* / GEOMETRY: *"35mm God's eye final settle"* — three different descriptions with a focal length mismatch.
* Avoid stacking redundant labels. Use ONE clean descriptor per shot:
  * ✅ *"24mm high-angle God's-eye wide shot"*
  * ❌ *"24mm EWS high-angle God's eye nadir crane descend lock-off"* — label overload that confuses AI video models.

## 🔍 29. THE CAMERA DIRECTION, PROP HANDOFF, TEMPORAL INTEGRITY & OFF-CAMERA DIALOGUE CODEX (V20.5 SSOT)

To eliminate the six most common spatial, temporal, and dialogue-visibility contradictions discovered through live QA testing:

### 1. 🎥 CAMERA TRACKING DIRECTION PARITY LAW:
* The camera's physical position relative to the characters (ahead / behind / alongside / overhead) MUST be 100% consistent across `[PROSE]`, `[CAMERA]`, and `[GEOMETRY]`:
  * If PROSE describes characters **running toward camera** (faces visible), CAMERA must say *"tracking backward ahead of the group"* and GEOMETRY must place characters in **foreground facing the lens**.
  * If PROSE describes characters **running away from camera** (backs visible), CAMERA must say *"tracking behind the group"* and GEOMETRY must place characters with **backs to the lens**.
  * **FORBIDDEN:** PROSE showing characters "bursting around a corner toward camera" while CAMERA says "chase behind the students" — this creates a 180° spatial contradiction.
* **SELF-CHECK:** For every tracking shot, ask: "Can the audience see their FACES or their BACKS?" The answer must be identical in all three blocks.

### 2. 🔄 EXPLICIT PROP OWNERSHIP TRANSFER & HANDOFF LAW:
* When a prop is introduced in Character A's possession and later used by Character B, the **causal handoff** must be explicitly described in `[PROSE]`:
  * ✅ *"Dito drags the chair into position; at 2.4s, Raka grabs the chair backrest from Dito and shoves it wedge-first beneath the door handle."*
  * ❌ *"Dito drags the chair... At 2.4s, Raka shoves the chair..."* — the chair teleports from Dito to Raka without a described transfer.
* This applies to ALL prop transfers: weapons, documents, tools, keys, bags, medical equipment, food items, etc.
* **RULE:** If Character A is holding Prop X, and later Character B is holding Prop X, there MUST be a described moment where A releases/passes and B receives/grabs.

### 3. ⏱️ ZERO-DURATION TEMPORAL WINDOW BAN:
* **STRICTLY FORBIDDEN:** Declaring a temporal window with identical start and end times (e.g., *"from 9.2s to 9.2s"* = 0 seconds = mathematically impossible).
* Every declared temporal window MUST have a non-zero positive duration:
  * ✅ *"From 9.2s to 10.0s, the living settle hold maintains..."*
  * ❌ *"From 9.2s to 9.2s settle-start..."* — zero-duration window that creates a temporal paradox.
* **SELF-CHECK:** For every temporal range "from Xs to Ys", verify Y > X.

### 4. 📐 SHOT COVERAGE MUST SPAN FULL DURATION (0.0s → [Duration]):
* Block 5 `[CAMERA]` MUST account for every second from 0.0s to [Duration] with no gaps and no overlaps:
  * If the final shot runs from 5.1s to 10.0s, declare it as such — do NOT end it at 9.2s and leave 9.2–10.0s undefined.
  * If a camera movement occurs within a shot (e.g., the camera settles into a lock-off at 9.2s), describe it as an **internal movement transition within the same shot**, not a new shot:
    * ✅ *"Shot 3 [85mm CU (5.1s–10.0s)]: Portrait close-up on Yara; at 9.2s, camera gradually settles into a static high-angle lock-off, holding through 10.0s."*
    * ❌ *"Shot 3 [85mm CU (5.1s–9.2s)]"* + undefined 9.2–10.0s gap.
* **RULE:** The sum of all shot timestamp windows = total clip duration. No second may be unaccounted for.

### 5. 🎙️ OFF-CAMERA DIALOGUE DECLARATION LAW:
* If a character speaks during a shot that is framed on a DIFFERENT character (e.g., Sari speaks during Yara's 85mm CU), the dialogue MUST be explicitly declared as **off-camera / off-screen**:
  * ✅ *"Sari whispers off-camera in natural conversational Jakarta Indonesian: \"Jangan buka pintunya!\""* — AI knows not to attempt lip-sync on an invisible speaker.
  * ❌ *"Sari whispers in natural conversational Jakarta Indonesian: \"Jangan buka pintunya!\""* during a shot where Sari is not visible — AI may hallucinate Sari's face into the frame or fail lip-sync entirely.
* **RULE:** If the speaking character IS visible in the current shot, use standard dialogue syntax with cultural dialect anchor. If the speaking character is NOT visible, prepend *"off-camera"* or *"off-screen"* to the dialogue tag.
* When off-camera dialogue is used, Block 3 `[ACTING]` should describe the LISTENING character's reaction (the one ON camera), not the speaking character's mouth.

### 6. 📐 SHOT-TYPE ANGLE CONSISTENCY WITHIN A SINGLE SHOT:
* If a shot begins as one angle/type (e.g., *"85mm CU"*) and transitions to a different angle (e.g., *"high-angle lock-off"*), the transition MUST be explicitly described as a **camera movement within the shot**:
  * ✅ *"85mm CU at eye-level; at 9.2s, the camera subtly tilts upward into a slight high-angle, settling into a static lock-off."*
  * ❌ *"85mm CU"* in CAMERA, then *"static high-angle lock-off"* in PROSE/TEMPORAL — the angle change appears from nowhere.
* **RULE:** Every change in camera height, angle, or movement mode within a single shot requires an explicit in-shot transition description with a timestamp.
